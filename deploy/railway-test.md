# Preparação Railway — testes fictícios

O projeto Railway **AbigailOvos-Teste** foi criado pelo utilizador e contém um serviço MySQL e o backend `abigail-api-teste`. O ambiente predefinido do Railway chama-se `production`, mas este projeto é **exclusivamente de teste** e não deve receber dados reais. Os serviços consomem os créditos do fornecedor; acompanhar a utilização no painel. Volumes de teste podem ser eliminados após a expiração dos créditos, conforme as condições do Railway.

O serviço API foi configurado com referências às variáveis do MySQL, sem publicar a base nem copiar a base habitual. Em 09/11/2026 não havia domínio HTTP nem proxy TCP público para o MySQL. O perfil `railway-test` destina-se apenas a este ambiente: o Railway termina HTTPS na borda e o backend recebe HTTP no trecho interno; o backend não confia em cabeçalhos encaminhados e os cookies são marcados como seguros. A proteção por endereço vê o endereço da ligação ao backend, que pode representar vários utilizadores. O perfil não é adequado para produção; a segurança, a autenticação ponta a ponta e o comportamento real no telemóvel ainda não foram integralmente validados.

Em 09/11/2026, o processo inicial não Web aplicou as migrações V1–V8 à base Railway de testes e terminou sem erro. A conta de administrador inicial foi criada usando credenciais fictícias escolhidas pelo utilizador. O processo de bootstrap recusa inicializar uma base que já contenha contas; não o repetir nem restaurar a configuração inicial em futuras implantações.

As credenciais de bootstrap foram removidas das variáveis atuais; bootstrap e migrações automáticas foram desativados e o backend foi iniciado em modo Web. Segredos presentes em configurações ou snapshots anteriores do fornecedor podem permanecer retidos segundo a sua política mesmo após remoção; usar apenas credenciais exclusivas de teste. Evitar reverter para a implantação inicial de bootstrap. O MySQL do template usa as credenciais disponibilizadas pelo Railway; o princípio de menor privilégio e a segurança do acesso precisam de revisão antes de produção.

Em 11/11/2026, o endereço público de teste ativo era `https://abigail-teste.up.railway.app/`. Uma consulta sem credenciais a `/api/me` devolveu HTTP 401 com certificado HTTPS verificado. Uma consulta autenticada com a conta administrativa de teste confirmou o acesso e a presença de três contas; as consultas de produtos e relatório devolveram HTTP 200. O APK debug `mobile/build/app/outputs/flutter-apk/AbigailOvos-Teste-Painel-V9.apk` foi instalado no Android CPH2197 com identificador separado `com.abigailovos.abigailovos.teste`, sem substituir a aplicação habitual. O utilizador confirmou a abertura e a persistência do stock. A impressão não foi testada numa impressora ou destino PDF.

A base habitual local continua em V4 e não foi alterada. A base Railway de teste foi migrada para V9 após uma cópia cifrada e restauro de validação; o backend novo está ativo e `DB_MIGRATIONS_ENABLED` voltou a `false`. O serviço auxiliar criado para a cópia e a chave SSH temporária foram removidos. A cópia final cifrada está em `C:\Users\HP\development\abigailovos-backups\railway-teste-antes-v9-20261111`; a chave de recuperação usa DPAPI e depende deste utilizador e desta instalação Windows. Não substitui uma cópia externa e plano de recuperação de desastre. Consultar [validacao-v9.md](../docs/validacao-v9.md).

Ao tentar pausar a API com a CLI, a configuração regional legada `iad` foi removida e o Railway iniciou temporariamente a API em US West. O serviço foi reconfigurado para US East, agora com identificador `us-east4-eqdc4a`, e está ativo com uma réplica. A base MySQL não foi movida. Confirmar eventuais implicações de região e custos no painel; não assumir que o identificador regional é igual ao anterior.

Não atualizar nenhuma base sem plano, cópia de segurança verificada e autorização. A migração V9 pode deixar alterações parciais em caso de falha. O projeto Railway está na internet e acessível publicamente apesar do login obrigatório: não inserir dados reais.

O código em desenvolvimento já contém a V10 e alterações de clientes, pendências, relatório e meios de pagamento, mas estas **não estão publicadas no Railway**. Foi compilado, mas não instalado, o APK debug isolado `mobile/build/app/outputs/flutter-apk/AbigailOvos-Teste-V10-Aguardando-Servidor.apk`, configurado para o Railway de teste e para apresentar o aviso de dados fictícios. O identificador `com.abigailovos.abigailovos.teste` e a assinatura debug correspondem ao APK V9 de teste. Não instalar esse APK antigo: o servidor Railway continua na V9. A cópia anterior à V9 não inclui eventuais alterações posteriores. Antes de atualizar, obter autorização e uma nova cópia consistente, verificar o restauro e coordenar a migração, o backend e o APK: ver [validação V10](../docs/validacao-v10.md).

Em 13/11/2026, com autorização do utilizador, foi recolhida uma **cópia preliminar** cifrada em `C:\Users\HP\development\abigailovos-backups\railway-teste-antes-v10-20261113`, enquanto a API de teste continuava ativa. A cópia foi autenticada e restaurada num MySQL independente; a V10 passou nesse restauro, preservando as vendas e as restantes tabelas verificadas. O serviço temporário de cópia foi removido, a instância MySQL local de restauro foi desligada e os seus dados temporários foram removidos. Nenhuma migração foi aplicada ao Railway; a API V9 continua ativa, com migrações e bootstrap desligados. O telefone não foi detetado por USB, pelo que a atualização coordenada ficou suspensa. Antes de prosseguir é necessária **outra cópia final**, obtida com as gravações suspensas e testada por restauro; a cópia preliminar não inclui eventuais alterações posteriores.

O isolamento de vendas por vendedor e a assistência administrativa foram acrescentados apenas ao código local e passaram em testes automáticos locais, mas não foram validados no telefone. **O Railway V9 continua a permitir que vendedores consultem e alterem vendas de outros vendedores.** Não usar dados reais. O APK V10 já compilado antecede estas alterações e não as contém; não o instalar como versão atualizada. O novo Mobile recusa usar as vendas com um backend que não confirme as capacidades, mas isso não protege os APKs antigos nem o acesso direto ao backend antigo. É necessária atualização coordenada, após testes e a cópia final verificada, com autorização.

A recuperação de vendedores acrescentou a migração V11 ao código local, ensaiada em MySQL isolado e fictício. Uma atualização futura precisa de ensaiar V10–V16 numa nova cópia restaurada; a validação preliminar de V10 não cobre V11. O Railway não foi alterado. Ver [recuperação de acesso](../docs/recuperacao-acesso.md).

O código local acrescenta agora a V12 para telefone obrigatório e único por cliente. A V12 recusa clientes existentes sem número válido ou com número repetido; os cenários válidos, inválidos e duplicados passaram em MySQL isolado e fictício. Antes de atualizar, é necessário identificar e resolver esses casos sem apagar histórico, além de ensaiar todas as migrações numa cópia final restaurada. O Railway V9 e o APK V10 anteriormente gerado não têm esta proteção. Ver [duplicados de clientes](../docs/duplicados-clientes.md).

O código local posterior inclui V13–V16 e login por sessões. Em 15/11/2026, por decisão do responsável, foi removido o segundo fator em toda a aplicação local; o administrador usa palavra-passe sem código, mas as tabelas e registos históricos são preservados. Passaram testes automáticos locais e ensaios MySQL isolados, mas a alteração ainda não foi publicada ou validada ponta a ponta. Em 15/11, `/api/me` respondeu HTTP 401 sem credenciais; isso não verifica a versão nem autenticação completa. A CLI Railway estava disponível, mas sem projeto ligado ao diretório. Um APK construído a partir do Mobile atual não tenta Basic automaticamente e não conseguirá iniciar sessão no Railway V9; o APK V10 antigo também não é a versão atual. Além disso, o perfil local `railway-test` mantém `abigail.security.session-mode=false`; publicar o backend com essa configuração não ativa sessões. É preciso confirmar projeto e ambiente, planear configuração segura de sessões e obter autorização específica para cada ação. Não atualizar o servidor, a base Railway ou um APK ligado a eles sem cópia final com gravações suspensas, restauro verificado e ensaio na cópia.

Em 15/11/2026, o telefone OPPO A74 5G foi ligado por USB. O identificador de teste anterior não constava na verificação; com autorização, foi instalado um APK debug com o mesmo identificador de teste, mas configurado para uma API HTTPS e base MySQL **novas e fictícias no computador**, acessíveis pelo USB. O login do vendedor fictício foi verificado no computador; a experiência no telefone ainda aguarda validação. Após a decisão de retirar o segundo fator, foi compilado outro APK que não pede código, ainda sem instalação autorizada. Este teste não altera, migra nem atualiza o Railway.
